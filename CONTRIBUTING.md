# Contributing

Thank you for contributing to `email-digging-skills`. Because this repository is a public, generic toolkit designed to run locally on sensitive customer data, contributions must keep strict boundaries between generic code and user-specific data.

Please follow the [Code of Conduct](CODE_OF_CONDUCT.md). If you discover a data-leak, masking-bypass, or security vulnerability, **do not open a public issue** — report it privately as described in [SECURITY.md](SECURITY.md).

## Development setup

1. Install **Node.js `>= 22.18`** and **`pnpm`** (`pnpm@12.23.0`).
2. Install dependencies:
   ```sh
   pnpm install
   ```
3. Wire up local Git hooks and verify your toolchain against synthetic fixtures:
   ```sh
   pnpm init-workspace --demo
   ```

TypeScript runs directly on Node.js via built-in type stripping (no compile or bundle step):
- Use **erasable TypeScript syntax only** (`tsconfig.json` enforces `erasableSyntaxOnly`): no `enum`, `namespace`, or constructor parameter properties.
- Import local files with explicit `.ts` extensions and use `import type` for type-only imports (`verbatimModuleSyntax`).
- Put shared pipeline contracts in [`scripts/lib/types.ts`](scripts/lib/types.ts) and keep [`docs/design/phase-1.md`](docs/design/phase-1.md) in sync.
- Stick to the existing minimal dependencies (`@duckdb/node-api`, `yaml`, and Node built-ins including `node:sqlite` and `node:test`).

## Git hooks and secret / email scanning

Running `pnpm init-workspace` sets `git config core.hooksPath .githooks` when `core.hooksPath` is unset. You can also set it manually:

```sh
git config core.hooksPath .githooks
```

The [`.githooks/pre-commit`](.githooks/pre-commit) hook runs two checks before every commit:
1. **`node scripts/check-staged-emails.ts`** — scans staged files across UTF-8, UTF-16, CP932, GB18030, `.xlsx` XML entries, and binary ASCII runs, rejecting any email address outside reserved test domains (`example.com`, `example.jp`, `example.net`, `example.org`, typo-test variants such as `example.con` and `example.co.jo`, `*.example`, `*.test`, `*.invalid`, `localhost`, and masked strings containing `*`).
2. **`gitleaks`** — optional locally (`gitleaks git --staged --redact --no-banner` runs automatically if `gitleaks` is on `PATH`, and warns if absent), **mandatory in CI** alongside `node scripts/check-staged-emails.ts --all`.

## Testing and synthetic fixtures

- **Tests use only `fixtures/`** or temporary directories created under `os.tmpdir()`. Never read `workspace/` or `.env*` in tests.
- Run the full test suite:
  ```sh
  pnpm test
  ```
- Deterministic synthetic fixtures (`fixtures/sources/`, `fixtures/overrides/`, `fixtures/expected.json`) are generated by [`scripts/make-fixtures.ts`](scripts/make-fixtures.ts). If you update fixture definitions, regenerate them with:
  ```sh
  node scripts/make-fixtures.ts
  ```
- All addresses in docs and fixtures must use `example.com`, `example.jp`, `example.net`, or `example.org` (plus `example.con` / `example.co.jo` for typo coverage). If a unit test in `scripts/**/*.test.ts` must test a real-provider domain typo rule directly, append the trailing comment `// email-scan:allow` on that line.

## Database migrations

- Schema DDL lives in [`schema/migrations/`](schema/migrations/).
- **Never edit an already-applied migration.** Add the next numbered `.sql` file (for example `0003_add_column.sql`).
- Keep core SQLite DDL portable to PostgreSQL as documented in [`docs/schema.md`](docs/schema.md) (ISO-8601 UTC text timestamps, JSON stored as `TEXT`).
- Any migration adding a table or column must also classify how [`scripts/lib/masked-copy.ts`](scripts/lib/masked-copy.ts) masks or redacts it (`mask-data` refuses unclassified schema fields).

## Adding a downstream provider

See [`providers/README.md`](providers/README.md) for the full adapter contract:
1. Create `providers/<name>/index.ts` exporting a default object that implements `Provider` from [`scripts/lib/types.ts`](scripts/lib/types.ts), with `name` matching the directory name (`export.ts --provider <name>` discovers it automatically).
2. Implement dry-run support first, reading from the database's consent views (`v_sendable_strict` by default) and keying operations by normalized email.
3. Keep all adapter logs and `PushPlan.notes` masked; full addresses may only be written to local files under `workspace/output/exports/`.
4. List required environment variable names in `envKeys`, document them in `providers/<name>/README.md` and `.env.example` (names only, never values), and add unit tests in `providers/<name>/index.test.ts` using synthetic fixtures.

## Privacy rule: nothing user-specific in the repository

Never commit or include in pull requests, issues, comments, or tests:
- Real email addresses, customer names, phone numbers, or unmasked exports (even from `output/masked/`).
- Real source slugs, product or event names, proprietary column mappings, provider instance URLs, `config.yaml`, or `.env` files.

## Pull request checklist

Use the [pull request template](.github/PULL_REQUEST_TEMPLATE.md) and run all three checks locally before opening a pull request:

```sh
pnpm typecheck
pnpm test
node scripts/check-staged-emails.ts --all
```

Also verify `git status` to ensure no local config, workspace artifacts, or non-`example.*` email addresses exist in untracked files.
